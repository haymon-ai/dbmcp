# CLAUDE.md

The privacy first MCP server for SQL databases. Supports MySQL, MariaDB, PostgreSQL, and SQLite.

## Build & Test Commands

```bash
cargo build                                    # debug build
cargo build --release                          # release build
DBMCP_DB_BACKEND=mysql DBMCP_DB_USER=root cargo run          # stdio transport
DBMCP_TRANSPORT=http DBMCP_DB_BACKEND=mysql cargo run         # HTTP on 127.0.0.1:9001
cargo run -- --config-file dbmcp.yaml --env-file .env         # YAML config + env file

cargo nextest run --workspace # unit + DB-free integration tests
cargo nextest run <name>      # single test
cargo nextest run --no-capture # with stdout
cargo test --doc --workspace  # doc tests (nextest cannot run them)

cargo clippy --workspace --tests -- -D warnings   # lint (warnings = errors)
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps   # docs (broken links = errors)
cargo fmt --check             # check formatting
cargo fmt                     # apply formatting

./tests/run.sh                # integration tests, newest version per backend (Docker + cargo-nextest required)
./tests/run.sh --all-versions # integration tests, every Supported version
./tests/run.sh --filter mysql # filter by backend
```

## Architecture

Cargo workspace: root binary (`dbmcp`) + 13 library crates under `crates/`. Workspace members use `"crates/*"` glob.

- **`src/main.rs`** — Binary shim. Installs mimalloc as the global allocator, owns `#[tokio::main]`, and calls `dbmcp_cli::run` with the binary's name and version.
- **`build.rs`** — Root build script. Passes `-fapple-link-rtlib` on macOS targets so the fat-LTO link keeps clang's builtins for ort's CoreML objects; delete once rust-lang/rust#164915 is fixed.
- **`crates/cli/`** (`dbmcp-cli`) — CLI crate; public API is the async `run(bin, version)` and the opaque `Error` (with `exit_code()`). `cli.rs` owns `run` (parse → `dbmcp_config::load` → tracing at the loaded log level → `server::serve`). `args.rs` hosts `Arguments`: only `--config-file` and `--env-file` (plus help/version), converted into `LoadOptions`. No setting has a flag. `server.rs` hosts `serve` (tunnel → backend adapter → transport → pool shutdown) and `shutdown_signal`. `stdio.rs` and `http.rs` each expose a transport `serve`, which runs until client disconnect or a shutdown signal. `probe.rs` owns `GET /healthz` (liveness) and `GET /readyz` (injected ping: shared in-flight, 1s cache, 2s deadline, 503 on shutdown; opaque body); `http.rs` merges its router beside `/mcp`, outside bearer auth and rmcp's Host/Origin validation.
- **`crates/config/`** (`dbmcp-config`) — layered loader plus the config types. `load(&LoadOptions)` calls `settings::read`, which picks and reads the env files (in order, chained, stop at first broken), then each YAML config file in order: parse, `${}`-interpolate, and validate its structure (keys, section shapes) alone against the embedded config schema (`assets/dbmcp.schema.json`, hand-written JSON Schema 2020-12, `boon`; value keywords are stripped at runtime and serve editors only), stopping at the first broken file. It then checks every set value from every source with `Kind::check` (cast, type, range, choices, path resolution; empty = unset), even values that lose or sit in inactive sections, reporting `InputError`s under `invalid settings:`. It returns `Settings`: each setting's winning `Value` and `Source` (non-empty process env > the last env file's value if non-empty > the last config file that sets it); no merged YAML tree. Relative paths resolve against the declaring config or env file's directory. The loader's `Resolver` then applies defaults and activation rules infallibly and runs `Config::validate()`, tagging diagnostics with each value's `Source`. Public interface: `load`, `LoadOptions`, `home_dir`, `Loaded`, `LoadError`, and the config types; every module is private. Modules: `options` (`LoadOptions`), `env` (`SETTINGS`: YAML key path ↔ optional `DBMCP_*` name (`None` for YAML-only settings, via `yaml_only`) ↔ `Kind`, which owns every value rule incl. enum choices), `rules` (`cast` checks one file's `privacy.rules` map: names, fields, keys folded by `ColumnRule::fold` into a `Key` (`Table`/`Schema`/`Full`), entity, operator; `resolve` turns the winning rules into `ColumnRule`s: fills short keys' leading segments from the backend and `database.name`, checks full keys' catalog, finds repeats; value-free reasons), `dotenv` (env file parser), `template` (`${}` engine), `interpolate`, `node` (spanned YAML tree via serde-saphyr), `schema` (structure-only config schema validation and value-free error rendering; tests tie the schema to `SETTINGS` and Rust defaults), `settings` (`read`, `Settings`, `InputError`: owns the file list picks, cross-source precedence, value checks, and error order; tests check docs YAML examples; private submodules `settings::pick` (`pick::files`: picks a file list (flags > comma list), resolves each path (`~` expands; a list from an env file resolves against that file's directory), and lazily yields each file's path and text, reading none after a failure), `settings::layers` (`EnvLayers`: process env above the env files; parses the picked env files, and offers a variable view for `${}` where empty is a value and a setting view for `DBMCP_*` where empty is unset) and `settings::files` (`ConfigFiles`: parses, interpolates, and structure-checks each picked YAML config file, stops at the first broken one keeping its structure errors, and yields a setting's value per file, last first)), `loader`, `source`, `log` (`LogLevel`). Also `Config`, `DatabaseConfig`, `HttpConfig` structs, `Transport` enum (`Stdio`, `Http`), `DatabaseBackend` enum (`Mysql`, `Mariadb`, `Postgres`, `Sqlite`; setting names in each enum's `CHOICES` table). Activation rules (which optional sections exist; SSH settings without `ssh.host`) and `privacy.rules` resolution (`rules::resolve`) run in the loader's `Resolver::build`; validation rules run in crate-private `Config::validate()`, which calls each section's `validate()` and owns cross-section rules (SSH on SQLite), accumulating `Result<(), Vec<Diagnostic>>`. `origin` module: `AllowedOrigins` mirrors rmcp's private `Origin` matching (`:*` port wildcard) for the HTTP CORS layer; `HttpConfig::validate()` rejects malformed entries.
- **`crates/sql/`** (`dbmcp-sql`) — Shared `SqlError` type, SQL read-only validation (`validation` module; `validate_read` takes the re-exported lineage `Dialect` and checks `SHOW` via `Show`), identifier quoting (`sanitize` module), `LIMIT`/`OFFSET` rewriting (`pagination` module), query timeouts (`timeout` module), the `Connection` trait shared by every backend (`connection` module), and version tiers (`support` module: `supported(backend)` lines, hand-edited with the CI matrix; `Line::parse` / `Line::from_version_num`, fork `Variant`, `classify` → `Tier` (`Supported`/`BestEffort`/`Unsupported`), `Tier::warning(rules)`; never refuses).
- **`crates/server/`** (`dbmcp-server`) — Shared MCP tool implementations (`tools` module) and `server_info()`. Reused by all three database handler crates. Type-erased `Server` wraps any handler implementing `ServerHandler + Pools` (`Pools`: `ping` the default database, `shutdown` the pools).
- **`crates/truncate/`** (`dbmcp-truncate`) — Domain-free character caps for a list of JSON values: `Caps` (per-string cap + budget for the serialized array, `None` = off), `fit` (cuts strings, drops trailing items past the budget → `Fitted { items, cut, dropped }`), `Window` (the budget while items arrive; keeps `items`, counts `rest`). Deps only `serde`, `serde_json`. The query-tool side lives in `dbmcp-server` `truncate`: `caps(max_cell_chars, max_response_chars)` (0 = off, budget minus `RESERVED_CHARS` for the envelope), `Truncation::new(cut, omitted)`, `HINT`.
- **`crates/privacy/`** (`dbmcp-privacy`) — Regex-based PII detection (47 built-in entity types covering personal, financial, government, contact, network, digital-identity, and crypto categories) tagged by `Category` (`Personal`, `Financial`, `Government`, `Contact`, `Network`, `DigitalIdentity`, `Crypto`), four anonymisation operators (`replace`, `mask`, `redact`, `hash`), and an `Analyzer::builder()` entry point for category-filtered registries. Wired into query tool output behind `PrivacyConfig`. No SQL dependency (only local dep: `dbmcp-config`). `cells` module: `Plan` (one `PlannedColumn` per output column: `Position::Action(PrivacyOperator, Entity) | Placeholder(Entity) | Global` + expected folded `name`) and positional redaction under it (`Cells` → async `Redactor::redact_cells` → JSON objects, or `ShapeError`): `Action` cells are rewritten whole (`NULL` kept), `Placeholder` cells all become `<ENTITY>` (`NULL` included), `Global` cells run global detection with the column name as context. `Redactor` holds two keyed `hash` operators: global detection's under `privacy.key` and the rules' under a subkey of it (`Operator::rule_hash`), so a literal hashed by global detection never matches a rule token. Backends reach it only through `dbmcp-policy`'s `Planned`. Canonical entity list: `crates/privacy/src/entity.rs` (`Entity` enum); registration order: `crates/privacy/src/recognizers/mod.rs` (`all()`).
- **`crates/policy/`** (`dbmcp-policy`) — Column-rules (`privacy.rules`) planner; the backends' only route to `dbmcp-sql-lineage` analysis. `Analysis::new(sql, DatabaseBackend)` + `step(entries)` drives the catalog loop (`Step::Missing(names)` pairs each `WrittenName` with its dialect's `RelationRef` (schema + name read once in `relation`: part counts, PostgreSQL folding and 63-byte truncation, bare MySQL names in the view's schema or the `connected_to` database; a name with no reading is recorded `Entry::Absent` by `step` itself), which `deny::names` also matches → backend fetches `Entry`s on its connection; `Step::Done(Analyzed)`; `CATALOG_ROUNDS` bound → `Rejection::CatalogRounds`; `mismatch(reason)` for lexical mismatches). `Analyzed` (opaque lineage): `statement()`, `target()`, `plan(config)` → `Planned<'c>` (a non-`Flow::Bare` column over ruled sources is `Placeholder(entity)`, its rules sharing the entity; a bare column keeps its pair, `hash` only when every source is hashed under it, else `replace`) or a value-free `Rejection` (unknown function or cast type, denied relation/`SHOW`, `EXPLAIN` of a ruled relation unless a plain `ExplainForm::Json`/`QueryPlan` form, any `ExplainForm::Analyze` on one, `CREATE INDEX` on a ruled relation, ruled column outside the output incl. view bodies (also under `DISTINCT`, a deduplicating set operation, or a set-returning function's arguments), conflicting pairs, write laundering (every computed ruled value; unnamed: `UnnamedLaundering`), unnamed created column, a chosen (`Chosen`) or server-filled (`Computed`: omitted default, generated, on-update, fired cascade `SET DEFAULT` or copy from a parent hashed otherwise; from `CatalogColumn` and `Relation` `cascades` facts, fail closed) value in a `hash`-ruled write target, a write to a relation or fired cascade child with triggers or rules while `hash` rules exist (`Trigger`)). `Planned` owns the result side: `check_first(names, origins)` → value-free `Unfit`, `redact(&Redactor, names, rows)` (refuses unchecked rows; prunes a plain `EXPLAIN` of a ruled relation to per-dialect value-free keys via `explain.rs` first, fail closed on unexpected shape; `prunes()` tells backends); backends only translate server-reported origins. `enforce` owns the fail-closed envelope every backend runs a planned statement in (`Access`, `Enforced`, `Executed`, `Stop<E>`: backend-only refusals in `E`, `Withheld(label)` from the backend's `echoing` label): `admit(redactor, access, read_only)` → `Admitted` (no redactor or a read-only write runs nothing), `Stop::split` for `Connection::with_connection`, `settle(tx, access, planned, echoing, executed)` → opaque `Run` (a refusal rolls back, a database error, at `COMMIT` too, is withheld when echoing and the plan withholds, reads roll back, writes commit; `tx` `None` outside a transaction block), `Admitted::finish(ran, window)` redacts. `catalog` owns what backends report (`Entry`, `Relation`, `CatalogColumn`, `Cascade`, `CascadeAction`, `Family`, `Member`): lineage's slim relation plus the write facts (column default/generated/on-update, triggers, reachable cascades, inheritance tree), every fact a field without a default (a backend that cannot know one states `true`); `step` splits each `Entry` into the lineage catalog and the planner's facts. Re-exports the lineage vocabulary backends build (`WrittenName`, `NamePart`, `Origin`, `RelationId`, `SourceRef`, `RelationKind`, `StatementKind`).
- **`crates/mysql/`** (`dbmcp-mysql`) — MySQL/MariaDB backend: connection pooling (`after_connect`: read-only mode's `SET SESSION TRANSACTION READ ONLY`, then a one-time `VERSION()` check: a `database.backend` mismatch warning, else a fork probe (`flavour::variant`, `aurora_version`) and a `support::classify` tier warning outside Supported), query operations, schema introspection, MCP handler via `rmcp::tool_router`. `flavour.rs`: pure `flavour::of(version)` (MySQL vs MariaDB from a `VERSION()` string; callers read it), `line`, `variant` and `BackendMismatch`. `policy.rs`: `privacy.rules` enforcement (session probe incl. `VERSION()` vs `database.backend` (mismatch refuses), lexical `sql_mode`/charset, `information_schema` catalog rounds incl. `TRIGGERS` and a recursive `REFERENTIAL_CONSTRAINTS` cascade walk, plan, execute, view-body recheck, value-free error allowlist; writes reading a view must be able to roll back; when `Planned::prunes()`, MySQL pins `SET SESSION explain_json_format_version = 1` around the transaction and restores `= DEFAULT` after, 1193 ignored).
- **`crates/postgres/`** (`dbmcp-postgres`) — PostgreSQL backend: per-database connection pool cache (moka; read-only mode: `default_transaction_read_only = on` startup option; one `after_connect` tier check per process, shared `Arc<AtomicBool>`: `server_version_num()`, `version()` fork/pre-release markers via `version.rs`, `aurora_version` probe), query operations, schema introspection, MCP handler. `policy.rs`: `privacy.rules` enforcement (session probe, `to_regclass`/`pg_attribute` catalog rounds incl. `pg_trigger`/`pg_rewrite` triggers and a recursive `pg_constraint` cascade walk, plan, execute with OID/attnum origin check, view-body recheck, inheritance-tree re-read (`FAMILY_SQL`: a ruled newcomer → `FamilyChanged`), exact value-free `SQLSTATE` codes, unknown codes withheld).
- **`crates/sqlite/`** (`dbmcp-sqlite`) — SQLite backend: single-file connection (once-guarded `sqlite_version()` tier check in `after_connect`), query operations, schema introspection, MCP handler. `policy.rs`: `privacy.rules` enforcement (pragma catalog rounds incl. `sqlite_schema` triggers and a recursive `pragma_foreign_key_list` cascade walk, plan, execute with column-origin check, value-free extended codes).
- **`crates/sql-lineage/`** (`dbmcp-sql-lineage`) — Catalog-aware column-level SQL lineage: `analyze(sql, Dialect, &Catalog)` binds output columns and role-tagged references (`Join`/`Filter`/`GroupBy`/`Sort`/`Window`/`Distinct`/`Generator`) to physical `relation.column` sources, each output and written column tagged with a `Flow` (`Null`/`Default`/`Bare`/`Derived`; `Flow::merge` at set operations, `VALUES` rows, repeated writes, `USING` keys); names missing from the caller's `Catalog` snapshot come back as `LineageError::Missing` (caller fetches, inserts, retries). Per-dialect `const` built-in function tables live in `functions/` (value-exposing built-ins deliberately absent; set-returning ones in `SET_RETURNING`) and set `FunctionUse.known`; cast target types (`CAST`, `::`, MySQL `CONVERT(…, t)`) resolve against the `types` module's per-dialect tables (`tsvector`, `tsquery`, `jsonpath`, pseudo-, extension, and user types absent; SQLite accepts any) and set `TypeUse.known`. View and materialized-view bodies expand through the same loop (names tagged `Origin::View` of the innermost view). `statement` module dispatches the tiers (`StatementKind`): queries; relations-only `DROP`/`TRUNCATE`/`CREATE INDEX`/`CREATE TABLE` without a query fill `Lineage.target` (a new name resolves through `Entry::Vacant`); `SHOW` (`show` module: tokens → closed `Show` enum; a `WHERE` or non-literal `LIKE` filter → `Unsupported`)/`DESCRIBE`; `EXPLAIN` carries the inner lineage and its `ExplainForm` (`explain` module: sqlparser options → closed `Json`/`QueryPlan`/`Analyze`/`Other`, strict: only the exact plain forms `explainQuery` builds are `Json`/`QueryPlan`, any `ANALYZE` in any spelling is `Analyze`). Writes fill `Lineage.writes` (one `TargetColumn` per written column with its sources): creates (`CREATE TABLE … AS`, PostgreSQL top-level `SELECT … INTO`, `CREATE [MATERIALIZED] VIEW`) and DML (`INSERT`/`UPDATE`/`DELETE`/`MERGE`; DML `WHERE` = `Filter`, `RETURNING` = output). Write targets carry identity on `bind::Rel.table` (set by `named` for catalog tables, never views or derived relations) and bind through `Tree::target`/`Tree::written`; DML scopes come from the named constructors `Level::dml` and `Level::upsert` (`excluded`). DDL with expressions or `CHECK`/`REFERENCES`, `DROP … CASCADE`, `VALUES()`/`VALUE()` in `ON DUPLICATE KEY UPDATE`, `MERGE … RETURNING`, a CTE before DML, and every other statement → `Unsupported`.
- **`crates/ssh/`** (`dbmcp-ssh`) — Embedded SSH client that tunnels database connections through a bastion via a loopback listener (`Tunnel::start` → `TunnelHandle`).
- **`crates/sqlx-json/`** (`sqlx-json`) — `RowExt` trait for type-safe row-to-JSON conversion. Per-backend implementations for `SqliteRow`, `PgRow`, and `MySqlRow`.
- **`charts/dbmcp/`** — Helm chart (HTTP transport only), published as OCI to `oci://ghcr.io/haymon-ai/charts/dbmcp` by the `ghcr-io-chart` release job after the `ghcr-io-image` job; `version`/`appVersion` bumped by cog with the crate version. `values.config` renders verbatim into the mounted `dbmcp.yaml`; the chart forces `DBMCP_TRANSPORT`, `DBMCP_HTTP_HOST`, `DBMCP_HTTP_PORT`, `DBMCP_HTTP_ALLOWED_HOSTS` via env. Tested by the `helm` job in `.github/workflows/ci.yml` (`ct lint` + kind `ct install` against an image built from the commit); `ct.yaml` and `artifacthub-repo.yml` live at the repo root.
- **`plugins/dbmcp/`** — Claude Code and Codex plugin (not a crate). Claude Code: `.claude-plugin/plugin.json` (manifest + `userConfig`) and `.mcp.json`; Codex: `.codex-plugin/plugin.json` and `mcp.codex.json` (`env_vars`, `startup_timeout_sec`). Both wire the npm launcher `@haymon-ai/dbmcp@X.Y.Z` (exact pin) with the same eight `DBMCP_*` env names. Skills under `skills/` (`setup`, `privacy`) are shared by both hosts. Both `plugin.json` versions and the three pins (`.mcp.json`, `mcp.codex.json`, `skills/setup/SKILL.md`) are bumped by cog with the crate version; the `haymon-ai/marketplace` marketplace installs from `master`, so a pin can name an unpublished version for the few minutes between the bump commit and the npm publish. Validation (`claude plugin validate --strict --profile directory plugins/dbmcp`) and version/env-name checks are manual before a release.
- **Transport**: `transport` setting (`DBMCP_TRANSPORT`, default `stdio`); no subcommands. `stdio` serves Claude Desktop/Cursor; `http` serves Streamable HTTP with CORS via axum + tower-http. HTTP options are ignored under stdio.

## Configuration

**Precedence**: process env (`DBMCP_*`) > env files (`--env-file` repeatable / `DBMCP_ENV_FILE` comma list; later file wins, a later empty value clears) > YAML config files (`--config-file` repeatable / `DBMCP_CONFIG_FILE` comma list; later file wins per setting, lists replace, null is a no-op) > defaults. Empty `DBMCP_*` values count as unset. No file is auto-discovered.

- Env vars are set by the MCP client (via `env` or `envFile` in server config)
- Every setting (YAML key, env name; `privacy.rules` is YAML only) is listed in `crates/config/src/env.rs` and in the all-settings table in `docs/content/docs/configuration/index.mdx`; each setting is explained on its feature page under `docs/content/docs/`
- `DBMCP_DB_READ_ONLY` defaults to `true` — write operations blocked unless explicitly disabled
- Pinning a database name (`database.name` / `DBMCP_DB_NAME`) hides the cross-database tools (`listDatabases`, `createDatabase`, `dropDatabase`) on MySQL/PostgreSQL
- `PrivacyConfig` is a top-level config section alongside `DatabaseConfig` and `HttpConfig`; `Config.privacy` is `None` exactly when the mode is `none`, just as `Config.http` is `Some` only for the `http` transport. The mode (`privacy.mode` / `DBMCP_PRIVACY_MODE`, `PrivacyMode`: `none | rules | full`) defaults to `full`; `rules` rewrites ruled columns only (no `Analyzer`: global cells and error text raw), `full` adds global detection. The operator (`privacy.operator` / `DBMCP_PRIVACY_OPERATOR`) defaults to `hash` (keyed tokens like `<EMAIL_ADDRESS_4e1f0dd69c51e84c>`). Optional category subset via `privacy.categories` / `DBMCP_PRIVACY_CATEGORIES` (YAML list or comma-separated kebab values; unset = all built-ins). `privacy.model` / `DBMCP_PRIVACY_MODEL`: NER model directory; setting it alone turns NER on under `full` (load fails closed). `categories` and `model` are ignored outside `full`; `categories` is still checked in every mode by the loader. A set, removed `DBMCP_PII_*` env name (`env::RENAMED`) stops startup naming its `DBMCP_PRIVACY_*` replacement.
- `privacy.rules` (YAML only): named column rules (`columns` of exact `[[catalog.]schema.]table.column` keys, required `entity`, optional `operator`) flattened into `PrivacyConfig.rules: Vec<ColumnRule>` by `rules::resolve` (operator resolved, keys folded by `ColumnRule::fold` and expanded to four segments: MySQL `def.<database.name>`, PostgreSQL `<database.name>.public`, SQLite `main.main`). Applies under `rules` and `full`, ignored under `none`; the last config file that sets it wins whole (`null` keeps, `{}` clears). `Resolver::build` runs `rules::resolve` in every mode, so short keys missing `database.name`, a full key's wrong catalog segment, and repeats (after expansion) stop startup; every backend enforces them (`crates/{sqlite,postgres,mysql}/src/policy.rs`).
- `privacy.key` / `DBMCP_PRIVACY_KEY`: HMAC key (≥ 32 bytes, raw UTF-8, checked in every mode by the loader) for the `hash` operator (global or any rule's), ignored otherwise; unset = random per-process key (tokens change on restart and across replicas).

## Code Style

This project follows the [Microsoft Pragmatic Rust Guidelines](https://microsoft.github.io/rust-guidelines/agents/all.txt).

- **M-MODULE-DOCS**: Every module MUST have `//!` documentation
- **M-CANONICAL-DOCS**: Public items MUST have `///` docs with `# Errors`, `# Panics` sections when applicable
- **M-FIRST-DOC-SENTENCE**: Summary sentence MUST be under 15 words
- **M-APP-ERROR**: Use `thiserror` for error type derivation
- **M-MIMALLOC-APPS**: Use mimalloc as global allocator

## Security Constraints

- **Read-only mode**: ONLY allow SQL prefixed with SELECT, SHOW, DESC, DESCRIBE, EXPLAIN (never `USE`, which `writeQuery` rejects too: it leaks to pooled connections; never `SHOW WARNINGS` / `SHOW ERRORS`: they replay the previous query's warnings, which quote values) (the wrapped statement must itself be read-only). **ALWAYS** block `LOAD_FILE()`, `SELECT INTO OUTFILE/DUMPFILE`. On MySQL/MariaDB, `readQuery`/`explainQuery` **MUST** reject executable comments (`/*! … */`, `/*M! … */`) and characters the tokenizer cannot read (the server starts a `--` comment only at an ASCII space or control character, sqlparser at any Unicode space such as U+00A0; the server ends a `--`/`#` comment at a NUL byte, sqlparser does not; `writeQuery` rejects these too): sqlparser drops `/*M!` and expands every `/*!` regardless of version, so it would validate other SQL than the server runs.
- **MULTI_STATEMENTS**: **NEVER** opt in to multi-statement execution for user SQL. sqlx 0.9 always requests the MySQL `MULTI_STATEMENTS` flag and cannot clear it, and PostgreSQL's simple-query protocol accepts several statements, so `readQuery`/`explainQuery` **MUST** keep their parse-level single-statement checks (`validate_read`, `validate_single_statement`). `writeQuery` has no such check (#307).
- **Parameterized queries**: **NEVER** interpolate user values into SQL strings. Use parameterized queries exclusively.
- **Identifier validation**: **ALWAYS** validate database/table names (alphanumeric and underscore). Never use string interpolation for identifiers — use proper quoting per backend.
- **PII redaction**: on-by-default defense-in-depth applied to the rows the query tools return (`readQuery`, `writeQuery`, `explainQuery`) and to tool error messages (regex only, no NER; `full` mode only). User docs: `docs/content/docs/privacy/` ("Data Privacy"). **MUST NOT** be removed or bypassed without an explicit user request. On by default (`privacy.mode: full`); operators choose `rules` or `none` via `privacy.mode` / `DBMCP_PRIVACY_MODE`. Global detection walks every string leaf at any depth inside `json`/`jsonb` columns; JSON object keys are preserved verbatim (only values are inspected; JSON types only, MariaDB/SQLite JSON is text). A column ruled by `privacy.rules` is instead rewritten whole by its rule's operator, `json`/`jsonb` included (keys too); `NULL` stays `null`. While rules exist, every statement the planner cannot prove safe is refused before it runs (fail closed), and database errors from statements touching a ruled relation (and from every PostgreSQL `CREATE INDEX`) are withheld unless their code is value-free; user docs `docs/content/docs/privacy/rules.mdx`.
- **Untrusted-data envelope**: every tool registered via `ToolSpec` has its text content, error messages included, wrapped in random per-call `<untrusted-data-{uuid}>` boundaries (`structuredContent` unchanged). **MUST NOT** be removed or bypassed without an explicit user request.
- **Plugin**: the plugin wiring (`plugins/dbmcp/.mcp.json`, `mcp.codex.json`) **MUST NOT** set `DBMCP_DB_READ_ONLY` or any `DBMCP_PRIVACY_*` env. Skills under `plugins/dbmcp/skills/` **MUST NOT** loosen a protection setting (`database.read_only`, `privacy.*`, `database.ssl*`, `ssh.strict_host_key_checking`, `ssh.known_hosts`, `http.*` exposure/auth) without the user's own explicit request for that setting, **MUST NOT** ask for, read, or write secrets, and **MUST** treat redacted values, `privacy.rules` refusals, and the untrusted-data envelope as final.

## Never Do

- **NEVER** use `unwrap()` — use `expect("reason")` or propagate with `?`
- **NEVER** interpolate user input into SQL — use parameterized queries or sqlx bind
- **NEVER** skip identifier validation for database/table names — always validate then quote
- **NEVER** enable `MULTI_STATEMENTS` on any database connection
- **NEVER** add features, refactor, or "improve" code beyond what was explicitly asked
- **NEVER** duplicate content from `CONTRIBUTING.md` — reference it instead
- **ALWAYS** use `thiserror` for new error types, not manual `impl Display`
