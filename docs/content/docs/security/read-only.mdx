---
title: Read-only mode
description: How read-only mode limits the tools and SQL an assistant can use
---

By default, <Dbmcp /> runs in **read-only mode**. This controls which tools the AI assistant can see and use.

## Setting

| YAML key | Env var | Type | Default | Description |
|----------|---------|------|---------|-------------|
| `database.read_only` | `DBMCP_DB_READ_ONLY` | boolean | `true` | Enable read-only mode |

> **Security note**: Read-only mode is **enabled by default**. In this mode, the `write` tool is hidden from the AI assistant. Only read tools are available, and `read` enforces SQL validation (`SELECT`, `SHOW`, `DESCRIBE`, `EXPLAIN` only). Set `DBMCP_DB_READ_ONLY=false` (or `read_only: false` under `database` in the config file) to enable write tools.

## Tool-Level Access Control

In read-only mode, the `write` tool is not registered with the MCP client. The AI assistant never sees them in the tool list, which prevents it from attempting write operations entirely.

When read-only mode is disabled, the full tool set becomes available. See [Tools](/tools#tool-availability) for the complete tool availability matrix.

## SQL Validation in `read`

The `read` tool enforces AST-based SQL validation as defence-in-depth. Only the following SQL operations are permitted:

- `SELECT` — read data from tables
- `SHOW` — view database and table metadata
- `DESCRIBE` / `DESC` — inspect table structure
- `EXPLAIN` — view query execution plans

`USE` is rejected, in `read` and in `write`: it would change the database of a pooled connection for later queries. Pass the `database` argument to target another database.

`SHOW WARNINGS` and `SHOW ERRORS` (including `SHOW COUNT(*) WARNINGS` and `SHOW COUNT(*) ERRORS`) are rejected in `read`: on MySQL and MariaDB they can return the warnings an earlier query raised on the same pooled connection, and a conversion warning such as `Truncated incorrect DOUBLE value: '...'` quotes the value that query read.

> **Limitation**: `write` only detects `USE` in SQL the parser can read. On MySQL and MariaDB, a `USE` that follows a statement the parser does not support (for example `DO 1; USE other`) still runs, because database connections accept multi-statement queries (see [Multi-Statement Blocking](/security#multi-statement-blocking)).

This validation is always enforced, even when read-only mode is disabled, preventing write statements from being smuggled through the read tool.

## Read-Only Transactions

`read` and `explain` run read-only in every mode, even when read-only mode is disabled. On MySQL, MariaDB, and PostgreSQL, they run every statement inside a `START TRANSACTION READ ONLY` transaction. The database itself rejects writes to data, including writes made by functions that pass validation, such as sequence functions (`nextval`), large-object functions, and user-defined functions. The transaction is always rolled back; on PostgreSQL this also keeps session settings changed by a query from carrying over to later queries.

In read-only mode, every database connection is also a read-only session, so the database rejects writes on every query <Dbmcp /> sends, not only `read` and `explain`. On MySQL and MariaDB, each new connection runs `SET SESSION TRANSACTION READ ONLY`; on PostgreSQL, each connection starts with `default_transaction_read_only = on`.

SQLite has no read-only transactions. Instead, in read-only mode the database file is opened read-only (`SQLITE_OPEN_READONLY`), so SQLite itself rejects every write, including writes to attached databases. When read-only mode is disabled, `read` and `explain` run under `PRAGMA query_only`; <Dbmcp /> switches it off again before the connection's next use.

## Blocked Operations

The following are always blocked regardless of mode:

- `LOAD_FILE()` — prevents reading files from the server filesystem
- `SELECT INTO OUTFILE` / `SELECT INTO DUMPFILE` — prevents writing files to the server filesystem
- Session locks (`GET_LOCK`, `pg_advisory_*`), backend signalling (`pg_cancel_backend`, `pg_terminate_backend`), and PostgreSQL server administration functions (`pg_reload_conf`, `pg_switch_wal`, replication slots, restore points, statistics resets) — read-only transactions do not stop these

On MySQL and MariaDB, `read` and `explain` reject executable comments (`/*! ... */` and MariaDB's `/*M! ... */`), even inside a string literal. The server runs the SQL inside them, so a query could otherwise hide a statement or function call from validation. Ordinary comments and optimizer hints (`/*+ ... */`) are allowed, except a comment the server reads differently from the validator: a `--` comment that starts with a control character or a non-ASCII space (such as a non-breaking space, U+00A0), and a `--` or `#` comment that holds a NUL byte. Put an ordinary ASCII space after `--`. `write` rejects these comments too, so they cannot hide a `USE`.

## Disabling Read-Only Mode

Read-only mode can be explicitly disabled if you need write access. Set the `DBMCP_DB_READ_ONLY` environment variable to `false`, or `database.read_only: false` in the config file. This makes `write` available to the AI assistant. Only disable read-only mode in environments where you trust the AI assistant to make changes to your data.
