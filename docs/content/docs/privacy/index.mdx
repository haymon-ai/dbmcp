The recording runs in `full` mode with the optional [Machine Learning](/privacy/machine-learning) model set, which is what turns names into `<PERSON>`; the built-in recognizers alone catch emails, phone numbers, IBANs, and the other [data types](/privacy/data-types).

Query results often contain sensitive data: personal data (often called PII, personally identifiable information) such as email addresses, phone numbers, and names, and business data such as IBANs, API keys, and VAT numbers. <Dbmcp /> finds these values (names with the optional [model](/privacy/machine-learning)) in tool output and rewrites them before the response reaches the AI assistant, so the assistant can still work with the shape of your data without seeing the sensitive values themselves.

The feature is **on by default** (privacy mode `full`). Set the [mode](#modes) to `rules` or `none` to narrow or turn it off.

<Callout title="Why on by default">
Peer database servers and redaction tools ship with redaction off. <Dbmcp /> deliberately does not: every response it returns leaves your trust boundary for the AI assistant's model provider. A wrong redaction is visible in the output and fixable with a setting; a leaked value cannot be taken back.
</Callout>

`hash` tokens change on every restart (and differ across replicas) unless [`privacy.key`](/privacy/redaction#hash-key) is set.

## How it works

1. **Detect.** Built-in recognizers scan every string value in the output for patterns such as email addresses, credit card numbers (with checksum validation), IBANs, national IDs, and secrets. They are grouped into categories, so you can limit detection to the kinds of data you care about. An optional machine-learning pass adds free-form names of people, places, and organizations.
2. **Rewrite.** Each detected span is replaced by the configured operator: a keyed hash token such as `<EMAIL_ADDRESS_3f9a1c07b2d4e855>` (`hash`, the default), a plain placeholder such as `<EMAIL_ADDRESS>` (`replace`), `*` masking (`mask`), or removal (`redact`).
3. **Return.** The rewritten result goes to the assistant. Your database is never modified.

For columns you know hold sensitive data, such as salaries, margins, or customer e-mails, [column rules](/privacy/rules) go further: every value of a named table column is rewritten, whatever it looks like and however the query reads it, and statements that could reveal those values in other ways are refused.

## What gets filtered

This section describes the `full` mode. The `rules` mode filters only [ruled columns](/privacy/rules), plus its refusals and withheld errors.

Redaction applies to the **rows the query tools return** — `read` results, `write` rows (for example from `RETURNING`), and `explain` output — and to **tool error messages** from every tool. Error messages run through the regex recognizers only; the optional NER pass is skipped so table, column, and schema names in database errors stay intact. With [column rules](/privacy/rules), statements that could reveal ruled values are refused, and database errors from statements touching a ruled table are replaced by a generic message unless their error code never carries a value. Logs, successful `objects` responses, and tool arguments are **not** affected. Because error messages are filtered too, a host name, IP address, or URL in a connection or [SSH tunnel](/features/ssh-tunnel) error comes back as a token (SSH tunnel failures are also logged in full); set the mode to `rules` or `none` while you diagnose it.

## Modes

| YAML key | Environment variable | Type | Default | Description |
|---|---|---|---|---|
| `privacy.mode` | `DBMCP_PRIVACY_MODE` | enum | `full` | Which protection the query tools apply: `none`, `rules`, or `full` |

- `none`: nothing is rewritten or refused. Rows and error messages come back as the database returned them.
- `rules`: only [column rules](/privacy/rules) apply. Ruled columns are rewritten and unsafe statements refused; nothing else is detected.
- `full`: column rules plus detection on every string value and error message, as described above. Setting [`privacy.model`](/privacy/machine-learning) adds the machine-learning pass.

The default is `full`. Any other value stops startup with the list of choices.

```yaml
privacy:
  mode: rules
  operator: mask
```

Or set `DBMCP_PRIVACY_MODE=rules` (and optionally `DBMCP_PRIVACY_OPERATOR=mask`); `DBMCP_PRIVACY_MODE=none` turns it off. See [Redaction](/privacy/redaction) for the operator, key, and categories.

## Limits

Treat privacy modes as a layer that reduces what the assistant sees in result rows; it is not a blanket guarantee that no sensitive string ever leaves the server. Pair it with database-level controls (least-privilege roles, column masking views) for sensitive datasets.
