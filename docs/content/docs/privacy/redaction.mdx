Choose how detected values are rewritten. For what the feature covers, how it works, and the `privacy.mode` setting, see the [Overview](/privacy).

## Settings

| YAML key | Env var | Type | Default | Description |
|----------|---------|------|---------|-------------|
| `privacy.operator` | `DBMCP_PRIVACY_OPERATOR` | enum | `hash` | Operator applied to detected PII spans; the fallback for rules without their own |
| `privacy.key` | `DBMCP_PRIVACY_KEY` | string | *unset (random per process)* | HMAC key for the `hash` operator, at least 32 bytes; ignored by the other operators, but checked whenever set |
| `privacy.categories` | `DBMCP_PRIVACY_CATEGORIES` | list | *unset (all built-ins)* | Category subset for detection |

These settings apply under `full` only and are ignored otherwise; under `rules`, `privacy.operator` is still the fallback for [column rules](/privacy/rules) without their own `operator`, and `privacy.key` keys their `hash` tokens. A set `privacy.key` that is blank or shorter than 32 bytes stops startup in every mode. Column rules (`privacy.rules`, YAML only) have their own page: [Rules](/privacy/rules); the machine-learning model (`privacy.model`) has its own page too: [Machine Learning](/privacy/machine-learning).

## How spans are rewritten

The configured operator decides how each detected span is replaced:

- `hash` (default) — keyed hash token per value, e.g. `<EMAIL_ADDRESS_3f9a1c07b2d4e855>`: the type plus the first 16 hex digits of HMAC-SHA-256 under `privacy.key`.
  - Equal tokens mean equal stored text; different tokens don't prove different values.
  - Tokens are one-way: they can't be decoded or used in a `WHERE` clause to find the original row.
- `replace` — entity-aware placeholder. For example, `jane.doe@example.com` becomes `<EMAIL_ADDRESS>`. Plan for this when downstream code parses query output: a column that previously held a plain email now holds the placeholder string for matching rows.
- `mask` — length-preserving `*` characters.
- `redact` — span removed (replaced with empty string).

## Overlapping detections

When two detections overlap, no part of either is left in clear text:

- A detection inside another is covered by the outer one, e.g. a name inside an email address becomes one `<EMAIL_ADDRESS>`.
- A structured match (email address, IBAN, URL, …) is never cut by a name, place, or organization match from the [machine-learning](/privacy/machine-learning) pass, however confident that match is.
- Otherwise the more confident detection stays whole and the other covers the rest. `Anna Schmidt anna@company.example`, with a name match running into the address, becomes `<PERSON> <EMAIL_ADDRESS>`.

## Hash key

The `hash` operator is keyed so its tokens work as pseudonyms: without the key, nobody can hash a guess such as a known email address and compare it with a token to learn the original value. Set `privacy.key` / `DBMCP_PRIVACY_KEY` to a secret of at least 32 bytes. The value is used as given (its UTF-8 bytes); generate one with:

```bash
openssl rand -hex 32
```

- **No key.** <Dbmcp /> draws a random key at startup. Tokens stay stable within one process but change on every restart and differ across replicas.
- **Replicas.** Give every replica the same key so the same value gets the same token everywhere.
- **Rotation.** Change the key and restart. Every token changes; old and new tokens can't be linked.

## Categories

`privacy.categories` / `DBMCP_PRIVACY_CATEGORIES` accepts a list of kebab-case category names (a YAML sequence, or comma-separated in the env var). Leaving it unset enables every built-in recogniser; passing a subset narrows the analyzer registry to recognisers tagged with at least one of the selected categories.

- `personal` — `DATE_OF_BIRTH`, `EMAIL_ADDRESS`
- `financial` — `BANK_ACCOUNT_UK`, `BANK_ACCOUNT_US`, `CREDIT_CARD`, `CVV`, `IBAN_CODE`, `ROUTING_NUMBER_US`, `SORT_CODE_UK`
- `government` — `COMMERCIAL_REGISTER_DE`, `DRIVER_LICENSE_US`, `DRIVING_LICENCE_DE`, `DRIVING_LICENCE_UK`, `HEALTH_INSURANCE_DE`, `ID_CARD_DE`, `ITIN`, `LICENSE_PLATE_DE`, `LIFETIME_PHYSICIAN_NUMBER_DE`, `MBI_US`, `MEDICAL_LICENSE_US`, `MEDICAL_PRACTICE_ID_DE`, `NHS_NUMBER`, `NINO_UK`, `NPI_US`, `PASSPORT_DE`, `PASSPORT_UK`, `PASSPORT_US`, `SIN_CA`, `SOCIAL_SECURITY_DE`, `TAX_ID_DE`, `TAX_ID_EIN`, `TAX_NUMBER_DE`, `US_SSN`, `VAT_NUMBER`, `VEHICLE_REGISTRATION_UK`
- `contact` — `PHONE_NUMBER`, `POSTCODE`, `POSTCODE_DE`, `POSTCODE_UK`
- `network` — `IP_ADDRESS`, `MAC_ADDRESS`, `URL`
- `digital-identity` — `API_KEY`, `JWT_TOKEN`, `PASSWORD_HASH`, `PRIVATE_KEY`
- `crypto` — `CRYPTO`

An empty list is rejected at startup. If the selected categories produce an empty registry, the analyzer falls back to the default registry and logs a warning so redaction is never silently disabled.

The NER entities follow the same filter: `PERSON`, `ORGANIZATION`, and `NATIONALITY_RELIGION_POLITICS` under `personal`; `LOCATION` and `FACILITY` under `contact`.

See [Data types](/privacy/data-types) for every entity type and [Machine Learning](/privacy/machine-learning) for names, places, and organizations.

## Nested JSON values

Redaction walks every string leaf in `json` and `jsonb` columns (and any other column the backend hands the server as a structured `serde_json::Value::Object` or `Value::Array`). A PII string redacts identically whether it arrives as a plain `text` column, a JSON literal cast to `text`, or a leaf nested inside a `jsonb` value at any depth. Non-string scalars (numbers, booleans, `null`) and the JSON shape (key names, array indexes, container ordering) are preserved.

JSON object **keys** are never inspected or modified — only values are redacted. A row like `{"jane.doe@example.com": "value"}` returns with the key intact. If you need key redaction, please open an issue; today's contract is values-only.

Exception: MariaDB and SQLite JSON is text, so it is scanned like any string, **keys included**, and a rewrite can leave invalid JSON. Context comes from the column name, not the key path. Use [`privacy.rules`](/privacy/rules) for such columns.
