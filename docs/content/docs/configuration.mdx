Database MCP reads its settings from `DBMCP_*` environment variables, an optional env file, and an optional YAML config file. The command line only names those files (`--config`, `--env`); there is no per-setting flag. This page is the reference for every setting. For the file formats, `${}` interpolation, and path rules, see [Config File](/docs/config-file).

The config file has a [JSON Schema](https://raw.githubusercontent.com/haymon-ai/dbmcp/master/crates/config/assets/dbmcp.schema.json) for editor completion and validation. Editors backed by the YAML language server (VS Code's YAML extension, JetBrains IDEs, Neovim, Zed) pick it up from this modeline on the first line of the file:

```yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/haymon-ai/dbmcp/master/crates/config/assets/dbmcp.schema.json
```

The `master` URL tracks the latest schema; replace `master` with a release tag such as `vX.Y.Z` to match an older binary. At startup `dbmcp` checks the file's keys and sections against the same schema and every value by its setting's type, so every value in the file must be valid even when a `DBMCP_*` variable overrides it.

## Precedence

Each setting is resolved on its own, highest priority first:

1. **Process environment** — `DBMCP_*` variables, typically set by the MCP client (via `env` or `envFile` in the server config)
2. **Env file** — `DBMCP_*` keys in the file named by `--env` / `DBMCP_ENV_FILE`
3. **Config file** — keys in the YAML file named by `--config` / `DBMCP_CONFIG`
4. **Built-in defaults** — backend-aware defaults described below

When the same setting is set in multiple places, the higher-priority source wins. An empty `DBMCP_*` value counts as unset at every layer, so it falls through to the next source; to set a setting to an empty string, use `key: ""` in the YAML file. Unknown `DBMCP_*` variables are ignored. See [Config File § Precedence](/docs/config-file#precedence) for a worked example.

## Value Formats

The **Type** column in the tables below determines how a value is written:

| Type | Environment variable / env file | YAML |
|------|---------------------------------|------|
| string | Text as-is | Any scalar; quote values YAML would read as another type (`password: "12345"`) |
| integer | Decimal digits | Integer (quoted digits also work) |
| seconds | Whole seconds as an integer | Integer |
| boolean | `true`/`false`, `1`/`0`, `t`/`f`, `TRUE`/`FALSE`, `True`/`False` | `true` / `false` (or a quoted string from the env set) |
| enum | One of the listed values, lowercase kebab-case, case-sensitive | Same |
| list | Comma-separated; items are trimmed, empty items are rejected | YAML sequence (`[a, b]` or one `- item` per line), or a comma-separated string as in the env var; replaces the default wholesale |
| path | Relative paths resolve against the working directory | Relative paths resolve against the YAML file's directory; leading `~` expands |

`yes`/`no`/`on`/`off` are **not** booleans and are rejected. A default of `—` or *unset* means the setting is absent until you set it.

## Transport

| YAML key | Env var | Type | Default | Description |
|----------|---------|------|---------|-------------|
| `transport` | `DBMCP_TRANSPORT` | enum | `stdio` | MCP transport: `stdio` or `http` |

`transport` defaults to `stdio`, which requires no additional configuration beyond the database settings below.

## HTTP Transport

These settings are only used when `transport` is `http`; the whole `http` section is ignored under stdio:

| YAML key | Env var | Type | Default | Description |
|----------|---------|------|---------|-------------|
| `http.host` | `DBMCP_HTTP_HOST` | string | `127.0.0.1` | Bind host for the HTTP server |
| `http.port` | `DBMCP_HTTP_PORT` | integer | `9001` | Bind port for the HTTP server |
| `http.allowed_origins` | `DBMCP_HTTP_ALLOWED_ORIGINS` | list | `http://localhost:*`, `http://127.0.0.1:*`, `http://[::1]:*`, `https://localhost:*`, `https://127.0.0.1:*`, `https://[::1]:*` | Allowed browser origins. Drives both CORS preflight and server-side `Origin` header rejection. Use `:*` to match any port or an explicit port (`https://app.example:443`); entries without a port are deprecated. Malformed entries are rejected at startup. An empty YAML list (`allowed_origins: []`) disables `Origin` validation for non-browser deployments; this is only expressible in YAML. |
| `http.allowed_hosts` | `DBMCP_HTTP_ALLOWED_HOSTS` | list | `localhost`, `127.0.0.1`, `::1` | Allowed host names. Enforced server-side; HTTP/2 `:authority` is honored. An empty list is rejected. |
| `http.auth_token` | `DBMCP_HTTP_AUTH_TOKEN` | string | *(unset)* | Bearer token required on every request (`Authorization: Bearer <token>`). Required for non-loopback binds. |
| `http.allow_unauthenticated` | `DBMCP_HTTP_DANGEROUSLY_ALLOW_UNAUTHENTICATED` | boolean | `false` | Allow a non-loopback bind without a token. Only behind a reverse proxy that authenticates callers. |

> **Security note**: Binding a non-loopback host (e.g. `DBMCP_HTTP_HOST=0.0.0.0`) without `DBMCP_HTTP_AUTH_TOKEN` is refused at startup. The `Origin`/`Host` allowlists defend against browser DNS rebinding only — they do not authenticate callers.

> **Security note**: The default `http.allowed_origins` accept browser pages served from **any port** on `localhost`/`127.0.0.1`/`[::1]`, so any local web app can call the server. On shared or development machines, set `DBMCP_HTTP_AUTH_TOKEN` or narrow `DBMCP_HTTP_ALLOWED_ORIGINS` to the explicit origins you trust (e.g. `http://localhost:5173`).

## Backend Defaults

Default values for `database.port` and `database.user` depend on the selected backend:

| Backend | Default Port | Default User |
|---------|-------------|-------------|
| MySQL | `3306` | `root` |
| MariaDB | `3306` | `root` |
| PostgreSQL | `5432` | `postgres` |
| SQLite | N/A | N/A |

SQLite does not use host, port, or user — only `database.name` (the file path) is required. In the YAML file, a relative SQLite path resolves against the file's directory; `:memory:` is passed through unchanged.

## Server Behavior

| YAML key | Env var | Type | Default | Description |
|----------|---------|------|---------|-------------|
| `database.read_only` | `DBMCP_DB_READ_ONLY` | boolean | `true` | Enable read-only mode |
| `database.max_pool_size` | `DBMCP_DB_MAX_POOL_SIZE` | integer | `5` | Maximum database connection pool size (at least 1) |
| `database.connection_timeout` | `DBMCP_DB_CONNECTION_TIMEOUT` | seconds | — | Connection timeout (at least 1; unset uses the driver default) |
| `database.query_timeout` | `DBMCP_DB_QUERY_TIMEOUT` | seconds | `30` | Query execution timeout (`0` disables it) |
| `database.page_size` | `DBMCP_DB_PAGE_SIZE` | integer | `100` | Max items per paginated tool response (range 1–500) |
| `log_level` | `DBMCP_LOG_LEVEL` | enum | `info` | Log level: `error`, `warn`, `info`, `debug`, `trace`. Logs go to stderr. |

> **Security note**: Read-only mode is **enabled by default**. In this mode, write tools (`writeQuery`, `createDatabase`) are hidden from the AI assistant. Only read tools are available, and `readQuery` enforces SQL validation (`SELECT`, `SHOW`, `DESCRIBE`, `USE`, `EXPLAIN` only). Set `DBMCP_DB_READ_ONLY=false` (or `read_only: false` under `database` in the config file) to enable write tools.

The page size applies uniformly to every paginated tool; see the [Cursor Pagination](/docs/features#cursor-pagination) section on the Features page for the full protocol.

## PII

Database MCP can rewrite detected PII spans inside query tool output. The feature is **opt-in and off by default** — applies to query tool response payloads (`readQuery` and any future query tools that route through the redactor) and to tool error messages (regex recognizers only, no NER pass). It is **not** applied to logs, successful schema-discovery responses, or tool arguments. See [Features](/docs/features#pii-redaction) for the supported entity list.

| YAML key | Env var | Type | Default | Description |
|----------|---------|------|---------|-------------|
| `pii.enabled` | `DBMCP_PII_ENABLE` | boolean | `false` | Enable PII redaction of query tool output |
| `pii.operator` | `DBMCP_PII_OPERATOR` | enum | `replace` | Operator applied to detected PII spans |
| `pii.categories` | `DBMCP_PII_CATEGORIES` | list | *unset (all built-ins)* | Category subset for the analyzer registry |
| `pii.ner_enabled` | `DBMCP_PII_NER_ENABLE` | boolean | `false` | Enable the optional ML/NER pass (person, location, organization, NRP & facility detection) |
| `pii.ner_model` | `DBMCP_PII_NER_MODEL` | path | *unset* | Path to the NER model directory (required with `pii.ner_enabled`) |

The other `pii` settings are ignored unless `pii.enabled` is true.

### Operator Values

`pii.operator` / `DBMCP_PII_OPERATOR` accepts one of the following values:

- `replace` — replace each detected span with an entity-aware placeholder (for example, an `EMAIL_ADDRESS` match becomes `<EMAIL_ADDRESS>`)
- `mask` — mask each detected span with `*` (length-preserving)
- `redact` — remove each detected span (replace with empty string)
- `hash` — replace each detected span with a stable hex digest (SHA-256)

### Category Values

`pii.categories` / `DBMCP_PII_CATEGORIES` accepts a list of kebab-case category names (a YAML sequence, or comma-separated in the env var). Leaving it unset enables every built-in recogniser; passing a subset narrows the analyzer registry to recognisers tagged with at least one of the selected categories.

- `personal` — `EMAIL_ADDRESS`
- `financial` — `BANK_ACCOUNT_UK`, `CREDIT_CARD`, `CVV`, `IBAN_CODE`, `ROUTING_NUMBER_US`, `SORT_CODE_UK`
- `government` — `ITIN`, `NHS_NUMBER`, `NINO_UK`, `PASSPORT_UK`, `PASSPORT_US`, `SIN_CA`, `TAX_ID_EIN`, `US_SSN`, `VAT_NUMBER`
- `contact` — `PHONE_NUMBER`
- `network` — `IP_ADDRESS`, `MAC_ADDRESS`, `URL`
- `digital-identity` — `API_KEY`, `JWT_TOKEN`, `PRIVATE_KEY`
- `crypto` — `CRYPTO`

An empty list is rejected at startup. If the selected categories produce an empty registry, the analyzer falls back to the default registry and logs a warning so redaction is never silently disabled.

### ML/NER pass (person, location, organization, NRP & facility)

The regex/checksum recognisers cannot catch free-form **person names**, **place names**, **organizations**, **nationality/religious/political groups**, or **facilities** — those have no fixed pattern. An optional machine-learning Named Entity Recognition (NER) pass adds `PERSON`, `LOCATION`, `ORGANIZATION`, `NATIONALITY_RELIGION_POLITICS`, and `FACILITY` detection on top of the regex layer. Which entities a given model can produce depends on its label set: a CoNLL model (e.g. `dslim/bert-base-NER`) yields person/location/organization, while an OntoNotes-class model additionally yields NRP and facility.

It is **opt-in at runtime**: the ML/NER code is always built into the binary, but stays inactive until both `pii.enabled` and `pii.ner_enabled` are true and a model directory is supplied.

Inference uses **ONNX Runtime** — there is **no external runtime library** to install: you need only the `dbmcp` binary and a model directory. The directory must contain:

- `config.json` (with an `id2label` map exposing at least one supported NER label: `PER`/`PERSON`, `LOC`/`GPE`, `ORG`/`ORGANIZATION`, `NORP`/`NRP`, or `FAC`)
- `tokenizer.json`
- `model.onnx`

Any other files in the directory are ignored — `dbmcp` reads only these three.

#### Set up a model locally

The quickest path is to download a model that has already been exported to ONNX. The steps below use the recommended English model, [`optimum/bert-base-NER`](https://huggingface.co/optimum/bert-base-NER) — an ONNX export of `dslim/bert-base-NER` (MIT licensed). It uses CoNLL labels, so it detects `PERSON`, `LOCATION`, and `ORGANIZATION`; [`protectai/bert-base-NER-onnx`](https://huggingface.co/protectai/bert-base-NER-onnx) is an equivalent alternative. NRP and facility detection require an OntoNotes-class model. v1 is English-only, but the pipeline is model-agnostic — any directory with the three files above works.

> **Note:** These pre-exported models are full-precision (fp32, ~430 MB). They need no Python toolchain to obtain, but an int8-quantized export is smaller and faster at inference if you can produce one.

**1. Download the model into a local directory** — either with the Hugging Face CLI (`pip install huggingface_hub`):

```bash
hf download optimum/bert-base-NER \
  --include config.json tokenizer.json model.onnx \
  --local-dir ./models/bert-ner
```

`--include` fetches only the three required files and skips the rest.

or with `git` + Git LFS (the `model.onnx` weights are LFS-tracked):

```bash
git lfs install
git clone https://huggingface.co/optimum/bert-base-NER ./models/bert-ner
```

or manually from the browser — open the model's [**Files and versions**](https://huggingface.co/optimum/bert-base-NER/tree/main) tab on Hugging Face and download `config.json`, `tokenizer.json`, and `model.onnx` with the download icon next to each, saving all three into one directory (e.g. `./models/bert-ner`).

**2. Confirm the required files are present:**

```bash
ls ./models/bert-ner
# config.json  model.onnx  tokenizer.json  (plus vocab.txt, tokenizer_config.json, … — ignored)
```

**3. Start `dbmcp` with the NER pass enabled, pointing at the directory:**

```bash
DBMCP_DB_BACKEND=sqlite DBMCP_DB_NAME=app.db \
DBMCP_PII_ENABLE=true DBMCP_PII_NER_ENABLE=true DBMCP_PII_NER_MODEL=./models/bert-ner \
  dbmcp
```

or, in a config file (relative paths resolve against the file's directory):

```yaml
database:
  backend: sqlite
  name: app.db
pii:
  enabled: true
  ner_enabled: true
  ner_model: ./models/bert-ner
```

**4. Verify it loaded.** Loading is **fail-closed**: a missing file or an unusable model makes the server refuse to start, so a clean startup means the model loaded. To confirm the pass is rewriting output, run a `readQuery` over a column holding a person or place name and check the value comes back as `<PERSON>` / `<LOCATION>` (with the default `replace` operator).

Behaviour notes:

- **Fail-closed.** If `pii.ner_enabled` is true but the model cannot be loaded, the server refuses to start. If inference fails mid-request, that request errors — it never silently falls back to regex-only.
- **Category-aware.** The NER pass respects `pii.categories`: `PERSON`, `ORGANIZATION`, and `NATIONALITY_RELIGION_POLITICS` are emitted only when `personal` is selected; `LOCATION` and `FACILITY` only when `contact` is. With no subset (the default), all apply. When the subset selects neither category, the model is not loaded at all.

> **Default**: redaction is off. Setting `DBMCP_PII_ENABLE=true` (or `pii.enabled: true` in the config file) is the only way to activate the redactor — `DBMCP_PII_OPERATOR`, `DBMCP_PII_CATEGORIES`, and the `DBMCP_PII_NER_*` settings alone have no effect.

## SSH Tunnel

Database MCP can reach MySQL, MariaDB, and PostgreSQL through an SSH server (bastion / jump host) using an embedded, pure-Rust SSH client — no `ssh` binary is needed. The tunnel is enabled when `ssh.host` / `DBMCP_SSH_HOST` is set.

| YAML key | Env var | Type | Default | Description |
|----------|---------|------|---------|-------------|
| `ssh.host` | `DBMCP_SSH_HOST` | string | — | SSH server host; enables the tunnel when set |
| `ssh.port` | `DBMCP_SSH_PORT` | integer | `22` | SSH server port |
| `ssh.user` | `DBMCP_SSH_USER` | string | — | SSH user |
| `ssh.password` | `DBMCP_SSH_PASSWORD` | string | — | SSH password |
| `ssh.key` | `DBMCP_SSH_KEY` | path | — | Path to SSH private key (OpenSSH, PKCS#1, PKCS#8, SEC1) |
| `ssh.key_passphrase` | `DBMCP_SSH_KEY_PASSPHRASE` | string | — | Passphrase for the SSH private key |
| `ssh.known_hosts` | `DBMCP_SSH_KNOWN_HOSTS` | path | `~/.ssh/known_hosts` | Path to known_hosts file |
| `ssh.strict_host_key_checking` | `DBMCP_SSH_STRICT_HOST_KEY_CHECKING` | enum | `yes` | Host key policy: `yes` rejects unknown hosts, `accept-new` trusts on first use, `no` disables verification (insecure) |
| `ssh.keepalive_interval` | `DBMCP_SSH_KEEPALIVE_INTERVAL` | seconds | `30` | SSH keepalive interval (`0` disables) |
| `ssh.local_port` | `DBMCP_SSH_LOCAL_PORT` | integer | ephemeral | Local tunnel port |

`ssh.user` and one of `ssh.password` / `ssh.key` are required with `ssh.host`. Setting any other `ssh` setting without `ssh.host` is a startup error, as is `ssh.key_passphrase` without `ssh.key`. A leading `~` in `DBMCP_SSH_KEY` and `DBMCP_SSH_KNOWN_HOSTS` expands to your home directory (in the YAML file, every path setting expands `~`); when no home directory can be determined, `ssh.known_hosts` must be set explicitly (unless the host-key policy is `no`). In YAML, an unquoted `strict_host_key_checking: no` is read as the string `no`, not a boolean, so it works as written.

**Docker:** inside the container `~` is the image's home directory, not yours. Mount the private key and a `known_hosts` file into the container (readable by the container user) and point `DBMCP_SSH_KEY` / `DBMCP_SSH_KNOWN_HOSTS` at the mounted paths. Avoid `accept-new` with `--rm` containers: every new container starts with an empty `known_hosts` and trusts the first key it sees on each launch.

```json
{
  "mcpServers": {
    "dbmcp": {
      "command": "dbmcp",
      "env": {
        "DBMCP_DB_BACKEND": "postgres",
        "DBMCP_DB_HOST": "db.internal",
        "DBMCP_DB_USER": "postgres",
        "DBMCP_DB_NAME": "mydb",
        "DBMCP_SSH_HOST": "bastion.example.com",
        "DBMCP_SSH_USER": "deploy",
        "DBMCP_SSH_KEY": "~/.ssh/id_ed25519"
      }
    }
  }
}
```

### How It Works

- Database MCP listens on `127.0.0.1:<port>` (ephemeral unless `ssh.local_port` is set) and points the database driver at it. Each database connection is forwarded over its own `direct-tcpip` channel on one shared SSH session.
- **`DBMCP_DB_HOST` and `DBMCP_DB_PORT` are resolved by the SSH server**, not locally — use the name or address the bastion can reach (e.g. `db.internal`, a private IP, or `127.0.0.1` for a database on the bastion itself).
- The SSH session opens lazily on the first database connection, so an unreachable SSH server does not prevent startup. Connecting, verifying the host key, and authenticating must finish within **10 seconds**.
- If the session drops, the next database connection reconnects it. Concurrent connections share one reconnect attempt.
- Keepalives are sent every `ssh.keepalive_interval` seconds; when keepalives go unanswered for about four intervals (~2 minutes at the default 30 s) the session is treated as dead. `0` disables keepalives (a silently dropped connection is then only noticed when the operating system gives up on it).

### Authentication

- **Password** (`DBMCP_SSH_PASSWORD`) and **private key** (`DBMCP_SSH_KEY`). When both are set, the key is tried first, then the password.
- Key formats: OpenSSH (plain or passphrase-encrypted), PKCS#1 RSA (including legacy AES-128-CBC encryption), SEC1 EC (unencrypted), PKCS#8 (plain or PBES2-encrypted).
- Key types: Ed25519, ECDSA (P-256, P-384, P-521), and RSA. RSA keys sign with `rsa-sha2-256`/`rsa-sha2-512`, as required by OpenSSH 8.8+.
- The key is read and decrypted once at startup; a wrong passphrase or unsupported format aborts startup.
- On Unix, a key accessible by group or others (any of the `0o077` mode bits set) logs a warning suggesting `chmod 600`; startup continues. No permission check is done on Windows.

### Host-Key Policies

The SSH server's host key is checked against `known_hosts` (re-read on every connect) before any credentials are sent.

| Value | Behavior |
|-------|----------|
| `yes` *(default)* | Only hosts already in `known_hosts` are accepted. Unknown hosts are rejected with the key's fingerprint and an `ssh-keyscan` hint. |
| `accept-new` | Unknown hosts are trusted on first use and appended to `known_hosts`. On Unix, a newly created file gets mode `0600` and newly created directories `0700` (subject to your umask); existing ones keep their permissions. A known host presenting a different key — including a key of a type not yet recorded — is rejected. |
| `no` | Verification is disabled (a warning is logged at startup). A changed key is accepted with a warning, but the password is withheld for that session. **Insecure**: exposes the tunnel to man-in-the-middle attacks. |

Keys marked `@revoked` are rejected under every policy, as long as `known_hosts` can be read. Under `no`, an unreadable `known_hosts` is ignored with a warning, so its `@revoked` entries no longer apply. `known_hosts` entries may be hashed (`|1|…`), use `[host]:port`, comma-separated host lists, and `*` / `?` / `!` patterns. See [SSH Host-Key Verification](/docs/security#ssh-host-key-verification) for the security implications.

### Database TLS Through the Tunnel

All `DBMCP_DB_SSL_*` settings work unchanged, and TLS stays end-to-end between Database MCP and the database. `DBMCP_DB_SSL_VERIFY_CERT=true` validates the certificate chain (against system roots and `DBMCP_DB_SSL_CA`) but not the hostname, so connecting via `127.0.0.1` does not cause a name mismatch.

**Limitation:** because the driver connects to an IP address, no TLS SNI is sent. Services that route on SNI (for example Neon's proxy) cannot be reached through the tunnel.

### Not Supported

- SQLite (rejected at startup)
- ssh-agent, keyboard-interactive / 2FA authentication
- `~/.ssh/config` parsing and `Host` aliases
- Multi-hop / `ProxyJump`, HTTP or SOCKS proxies in front of SSH
- Host-key fingerprint pinning (use a dedicated `known_hosts` file instead)
- DSA keys, FIDO/security-key (`sk-*`) keys, user certificates
- Host certificates and `@cert-authority` entries
- Hostname-verifying database TLS (`verify-full`)

### Troubleshooting

**Unknown host key** — under `yes`, the error names the fingerprint and suggests a command:

```text
SSH host key for bastion.example.com (SHA256:…) is not in /home/me/.ssh/known_hosts; verify the fingerprint, then run `ssh-keyscan -p 22 bastion.example.com >> /home/me/.ssh/known_hosts`
```

Compare the fingerprint with one obtained out-of-band (e.g. from the server's console via `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`) before running the suggested command.

**Host key does not match** — `… does not match <file>:<line>; the server may be impersonated`. If the server was legitimately re-keyed, remove the old entry with `ssh-keygen -R <host>` (or `ssh-keygen -R '[host]:port'`) and add the new one.

**Unsupported or legacy key encryption** — `SSH key <path> uses an unsupported encryption format; re-encrypt it with ssh-keygen -p -f <path>`. This covers legacy PEM keys encrypted with AES-256 or 3DES, encrypted SEC1 EC keys, and PKCS#8 PBES1. `ssh-keygen -p` rewrites the key in the OpenSSH format. An encrypted key without `DBMCP_SSH_KEY_PASSPHRASE` fails with `SSH key <path> is encrypted; set DBMCP_SSH_KEY_PASSPHRASE`.

**Unsupported key types** — DSA, FIDO (`sk-ecdsa-…`, `sk-ssh-ed25519-…`) keys, and certificates cannot be loaded. Use an Ed25519, ECDSA, or RSA key.

**`DBMCP_SSH_HOST is not supported with the sqlite backend`** — SQLite is a local file; remove the `DBMCP_SSH_*` settings.

**Tool errors ending in `(SSH tunnel: …)`** — when the database cannot be reached and the tunnel has an unresolved failure (connect timeout, authentication, host key, channel open, or a lost session), the cause is appended to the tool error, e.g. `… (SSH tunnel: SSH authentication failed for deploy@bastion.example.com:22)`. Other errors (SQL errors, read-only rejections) never get the suffix. It disappears once a connection through the tunnel succeeds. Failed connects are also logged with their full error chain at `error` level; a lost session is logged at `warn`.

**Windows: `os error 10013` with `DBMCP_SSH_LOCAL_PORT`** — the port falls in a range Windows reserves (often for Hyper-V/WSL). List reserved ranges with `netsh interface ipv4 show excludedportrange protocol=tcp`, pick a port outside them, or leave `ssh.local_port` unset to use an ephemeral port.

**Windows: a different `known_hosts` than `ssh` uses** — Database MCP resolves `~` from `USERPROFILE`. Win32-OpenSSH (`ssh.exe` in `System32`) uses the Windows profile directory even when `USERPROFILE` is overridden, and Git Bash's `ssh` uses `$HOME`, so they may read a different `known_hosts`. Set `DBMCP_SSH_KNOWN_HOSTS` explicitly to share one file. A `known_hosts` created outside your profile inherits that folder's permissions.

## Client Configuration Examples

MCP clients configure servers through JSON files. Each tool uses a slightly different file path, but the format is nearly identical. The examples below connect to a local MySQL database.

### Claude Code

Create a `.mcp.json` file in your project root:

```json
{
  "mcpServers": {
    "dbmcp": {
      "command": "dbmcp",
      "env": {
        "DBMCP_DB_BACKEND": "mysql",
        "DBMCP_DB_HOST": "localhost",
        "DBMCP_DB_USER": "root",
        "DBMCP_DB_PASSWORD": "secret",
        "DBMCP_DB_NAME": "myapp"
      }
    }
  }
}
```

*To enable PII redaction, add `"DBMCP_PII_ENABLE": "true"` and optionally `"DBMCP_PII_OPERATOR": "<replace|mask|redact|hash>"` (and `"DBMCP_PII_CATEGORIES": "<personal,financial,...>"` to scope detection) to the `env` map.*

Claude Code also supports HTTP transport for remote servers:

```json

  "mcpServers": {
    "dbmcp": {
      "type": "http",
      "url": "http://127.0.0.1:9001/mcp"
    }
  }
}
```

**File locations**: `.mcp.json` (project, shareable) · `~/.claude.json` (user, global)

## Migrating from CLI flags

Earlier releases accepted one CLI flag per setting. Those flags are gone: passing one now fails with clap's `error: unexpected argument '--db-backend' found` (exit code 2). The only flags left are `--config`, `--env`, `-h`/`--help`, and `-V`/`--version`. `--transport` and `--log-level` moved too: use `DBMCP_TRANSPORT` / `transport` and `DBMCP_LOG_LEVEL` / `log_level`.

Other behaviour changes to check while migrating:

- **Booleans are stricter.** Boolean env vars used to accept `yes`/`no` and `on`/`off` in any case. They now accept only `true`/`false`, `1`/`0`, `t`/`f`, `TRUE`/`FALSE`, and `True`/`False`; anything else fails startup. A bare boolean flag such as `--pii` becomes `DBMCP_PII_ENABLE=true`.
- **Empty values mean unset.** An empty `DBMCP_*` value counts as unset and falls through to the next source. In particular, `--allowed-origins ""` used to disable `Origin` validation; that is now only possible with `allowed_origins: []` under `http` in the config file.
- **Lists** keep the comma-separated env format; in the config file, write them as YAML sequences.

Before — settings passed as arguments in `.mcp.json`:

```json
{
  "mcpServers": {
    "dbmcp": {
      "command": "dbmcp",
      "args": [
        "--db-backend", "postgres",
        "--db-host", "localhost",
        "--db-user", "postgres",
        "--db-name", "myapp",
        "--pii",
        "--log-level", "debug"
      ]
    }
  }
}
```

After — the same settings as environment variables:

```json
{
  "mcpServers": {
    "dbmcp": {
      "command": "dbmcp",
      "env": {
        "DBMCP_DB_BACKEND": "postgres",
        "DBMCP_DB_HOST": "localhost",
        "DBMCP_DB_USER": "postgres",
        "DBMCP_DB_NAME": "myapp",
        "DBMCP_PII_ENABLE": "true",
        "DBMCP_LOG_LEVEL": "debug"
      }
    }
  }
}
```

To keep the settings in a file instead, move them into a YAML file and point at it with `"args": ["--config", "/abs/path/dbmcp.yaml"]`; see [Config File](/docs/config-file).
